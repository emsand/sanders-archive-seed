0 What code even is

Three languages, one page

Every one of your apps is a web page — the same kind of thing a browser opens. And every web page is made of three languages, each with one job.

HHTML — the structurethe words and boxes that are on the page▸

HTML lists what exists: a heading here, a button there, an empty box to hold a story. Think of it as the skeleton. On its own it's plain and unstyled — just the bones.

CCSS — the lookscolors, fonts, spacing, layout▸

CSS is the paint and the layout: this is peach, that font is rounded, leave this much space. Change one CSS line and the whole app can re-color. It never changes what is on the page, only how it looks.

JSJavaScript — the behaviorwhat happens when someone taps▸

JavaScript (or "JS") is the actions: when a child taps a choice, show the next page; play the narration; remember the streak. It's the part that makes the app do things instead of just sit there.

How the browser puts them together

When someone opens your app, the browser reads the HTML from top to bottom (building the boxes), applies the CSS (painting them), and runs the JavaScript (which fills the empty boxes with real stories and wires up the taps). That order matters, and you'll see it directly in the next module.

The one big idea of this whole course: your apps deliberately keep three things apart — the shell (empty boxes), the content (the stories, as plain data), and the engine (the code that puts the content into the boxes). Almost everything you'll want to change is content, and content is the safest, friendliest part to touch.

✓
You learned: a page is HTML (structure) + CSS (looks) + JavaScript (behavior) — and your apps separate the shell, the content, and the engine.
1 The simple shape

An engine app, layer by layer

Four of your apps share one clean design. We'll use My Brave Words as the example, but My School Story, My Fast Brain, and My Whole Story are built the exact same way.

Open its folder (my-brave-words/) and it's really just four pieces. Click each layer to see what it does:

1The Shellindex.html · ~227 lines▸

A small HTML file with almost nothing visible in it. It sets up the header, a single empty box for the story, the footer, and the pop-up dialogs. Then it loads the engine. This is the "page" — and it's tiny on purpose.

2The Engineapp.js · ~890 lines▸

One JavaScript file with all the smarts: it loads a story, draws each page, handles the choice tap, plays narration, tracks progress, switches English/Spanish. You rarely need to touch this — it's the machine that runs every story.

3The Contentstories/*.json · one file per story▸

Each story is its own small data file (we'll dissect one in Module 2). This is where the words, choices, and pictures live. Add a story = add a file here and list it. This is the part you'll actually edit.

4The Commercefamily.js · identical in all four apps▸

A shared add-on that handles grown-up sign-in and the family plan (accounts, unlocking premium features). It's byte-for-byte the same file in all four apps — a drop-in you don't customize.

the Engine reads the Content and fills the Shell ↓

See the shell for real

Here's the important part of that 227-line shell file. Notice how little there is:

my-brave-words/index.html
<!-- the header, footer, and dialogs live up here -->

A<main id="stage" class="stage"></main>

B<script src="app.js"></script>
C<script src="family.js"></script>
  • A
    The one empty box. The whole visible app — every story, page, and choice — gets drawn inside this single <main>. It starts empty; the engine fills it.
  • B
    Load the engine. This line pulls in app.js (the 890-line machine). "src" just means "the source file is over there."
  • C
    Load the commerce add-on. Same idea — the shared sign-in/plan code.

One line controls the whole color

Remember CSS is the looks. Each of the four apps is the same engine in a different color — and the color is basically one line. In my-brave-words/styles.css:

my-brave-words/styles.css · line 7
--accent: #ffd166;  /* the gold that themes Brave Words */

That --accent is a variable — a named value reused all over the stylesheet. Change this one line and buttons, highlights, and accents all shift together. Here's the real accent color of each app in the family:

My Brave Words · #ffd166 My School Story · #60A4CD My Fast Brain · #a78bdb My Whole Story · #7a4fae
Try it Two tiny, safe edits
  1. Open my-brave-words/stories/the-big-mad.json in your editor. Find the "title" near the top and change the English text to anything you like. Save, reload the app — the story's name changed, and you never touched code.
  2. Open my-brave-words/styles.css, change --accent on line 7 to #60A4CD (the blue), save, reload. The whole app re-themes.
💡 Can't break it: if anything looks off, undo (Ctrl+Z) or, if you've committed, git checkout . puts everything back. Module 6 covers safe experimenting in depth.
✓

2 A story is data

Inside one story file

This is the friendliest, most useful thing to understand: a story isn't code at all. It's a tidy list of labeled boxes. Change what's in a box, change the app.

Here's the real top of the-big-mad.json. Don't worry about the punctuation — read the labels:

my-brave-words/stories/the-big-mad.json
{
  "id": "the-big-mad",
  "icon": "🌩️",
  A"title": { "en": "The Big Mad", "es": "El gran enojo" },
  "tagline": {
    "en": {
      B"literal":    "A big mad feeling is real. It comes, and it goes.",
      "figurative": "The Big Mad is a storm cloud...",
      "simple":     "A big mad comes. A big mad goes."
    }, "es": { /* the same three, in Spanish */ }
  },
  C"steps": [
    { "icon": "🧱", "art": "assets/bm_fall.webp",
      "text": { "en": { "literal": "I worked a long time on my tower..." } } }
  ]
}
  • A
    Everything is bilingual. Almost every piece of text is a pair — "en" and "es". That's how one file serves both languages. To fix a Spanish typo, you edit the "es" box right next to the English one.
  • B
    Three reading levels. Big feelings text comes in literal, figurative, and simple — that's what the "Literal" button in your app switches between. Same idea everywhere.
  • C
    The pages are a list. steps is the sequence of story pages. Each step has an icon, a picture (art), and its text. Add a step, add a page.

The rest of the shape

Further down, the same story file holds a few more labeled boxes — the parts that make it interactive:

  • choice — the decision point: a prompt and an options list. Each option is marked good: true or good: false and carries its own outcome text (what happens when a child picks it).
  • vocab — the feelings word to learn: the word, a badge picture, a kid-friendly definition, and a little review quiz.
  • parent — the grown-up corner: what was practiced, a conversation starter, and a link to the printable.
Why this is the safe zone. Editing a story never touches the engine. The worst that happens is a typo in a sentence — visible instantly, fixed instantly. This is where you can build real confidence.
Try it Rewrite an outcome
  1. In the-big-mad.json, scroll to "choice" and find the options.
  2. Pick the good: false option and reword its "outcome" English text to be gentler.
  3. Save, reload, play the story, and pick that choice to see your new words appear.
💡 Keep the quote marks and commas exactly where they are — those are the "walls of the boxes." If the story fails to load, you likely deleted a " or ,; undo and try again.
✓
You learned: a story is data, not code — labeled boxes, bilingual en/es, three reading levels, steps for pages, and choice/vocab/parent for the interactive parts. Editing content is the safe zone.
3 Two variations

Same idea, packaged differently

Once you can see "shell + engine + content," you'll spot it everywhere — even when it's dressed differently. Two of your apps are useful variations.

Eli Walks With Me — content is a conversation

Eli has the same layered shape (a shell, an app.js engine, and stories/*.json content), but a story here is a scripted dialogue instead of pages. Look at how the content names its speakers and tags each line:

eli-walks-with-me/stories/the-kind-no.json
A"speakers": {
  "eli":    { "name": "Eli",    "kind": "guide" },
  "maya":   { "name": "Maya",   "kind": "child" }
},
"screens": [
  { "number": 1, "title": { "en": "We Finished It" },
    "lines": [
      { "speaker": "eli",
        B"modes": ["full-guide", "light-guide", "child-leads"],
        "text": { "en": "..." } }
    ] }
]
  • A
    A cast list. Each story declares who's speaking — Eli the guide, and the child. Lines then point at a speaker by name.
  • B
    Guide levels are built in. Each line lists which modes it appears in. That's how the same script plays as "Full Guide," "Light Guide," or "Child Leads" — the engine simply shows the lines whose modes match.

Treasures That Teach — everything in one file

Treasures folds the engine and the content into a single page, stories.html. (Its index.html is just the funder pitch page.) The stories live in a list that starts at line 497:

treasures-that-teach/stories.html · line 497
const STORIES = [
  { n:1, slug:'i-am-what-i-am', tint:'#d7e4c8',
    title:{en:'I Am What I Am', es:'Soy lo que soy'},
    pages:[
      { Akind:'text', t_en:"Zola's family moved to a new town...",
        Bt_literal_en:"Zola's family moved... Zola felt very nervous." },
      { kind:'choice', good_en:"Go as Zola..." }
    ] }
]
  • A
    Pages have a type. kind:'text' is a story page; kind:'choice' is a decision. Same "list of pages" idea as the engine apps, just written a little differently.
  • B
    The "Literal" toggle lives in the data. The plain-language version of a figurative sentence sits right beside it as t_literal_en. The accessibility button just swaps which one shows.

That accessibility toolbar (Literal, dyslexia font, text size, dark mode, word-by-word narration) works by a simple trick you can now understand: each button flips a setting and remembers it in the browser's little memory, called local storage, under a key like ttt_literal. Next visit, it reads the memory and restores your choice.

Try it Meet the app's memory
  1. Open your Treasures app, press F12 to open the browser's developer tools, and click the Application tab (Chrome/Edge) or Storage (Firefox).
  2. Under Local Storage, find the keys starting with ttt_.
  3. Toggle the "Aa" dyslexia-font button in the app and watch ttt_font change from 0 to 1. That's the app writing to its own memory.
✓
You learned: Eli is the layered shape with dialogue content (speakers + lines + guide modes); Treasures is the one-file shape (engine + a STORIES list together), and settings persist in local storage.

"Where am I?" — the state

Every app needs to remember what's on screen. In the flagship it's one small object called state (line 4933):

index.html · line 4933
const state = {
  currentStory: null,   // which story is open
  currentPage: 0,       // which page we're on
  choiceMade: false,    // has the child picked yet?
  lang: 'en'            // English or Spanish
};

Read it in English: "no story open yet, on page 0, no choice made, language is English." Every time you tap, the engine updates this little note and redraws. That's the entire mental model of how the app moves.

Try it Find and edit in the big file
  1. Open index.html, press Ctrl+F, and search for const STORIES — that jumps you to line 3279.
  2. Change story id:0's title from "Oops, I Did It" to anything.
  3. Save and reload your local flagship. The story's name changed — in a 10,000-line file, you found and edited exactly the right spot.

5 How it ships

The plumbing that gets it online

A few small files show up in every app. You don't edit them often, but knowing what each does removes the last of the mystery — and these are exactly the pieces behind the fixes from earlier today.

  • sw.js — the offline cache. The "service worker." It quietly saves the app so it still opens with a weak connection. The mbf-v97 line inside is a version stamp; bumping it forces everyone onto the newest copy.
  • gen-csp.mjs / build-editions.mjs — the security step at publish time. These run when the app deploys and write the security rules (the "Content-Security-Policy") that say which code is allowed to run. This is the file we fixed today — it now handles line-ending differences so nothing gets wrongly blocked.
  • netlify.toml — the publishing recipe. Tells Netlify (your host) how to build the site, which folder to put online, and what to cache. A short settings file.
  • manifest.json — the "install to phone" card. Name, icon, and colors so the app can be added to a home screen and open like a real app.
  • functions/ — a tiny backend. Small programs that run on the server, not in the browser. tts.js is the one that talks to the ElevenLabs voice service while keeping the secret key hidden from users.

From your edit to the live site, in one breath

You edit a file → you git push (send the change up) → Netlify notices, runs the build recipe (including the security step) → about a minute later, the live site updates. That's the whole pipeline you've been watching happen today.

6 On your own

Your exploring toolkit

You now know enough to poke around any app with confidence. Here's how to do it safely and find your way.

Rule one: you can always get back

  • Undo is instant: Ctrl+Z reverses any edit you just made.
  • Git is a safety net: before experimenting, your saved commit is a snapshot. git checkout . throws away un-saved changes and restores every file. Nothing you try between commits is permanent.
  • Start small and visible: text and colors first — you'll see the result immediately, so mistakes are obvious and harmless.

The browser's developer tools (your X-ray glasses)

Press F12 in any browser to open them. Three tabs are worth knowing:

  • Elements — the live HTML. Hover over a line and the matching thing highlights on the page. Great for "what is this box called?"
  • Console — messages and errors the app prints. You saw this today: the red "Refused to execute inline script" lines were the console telling us exactly what was blocked.
  • Application → Local Storage — the app's little memory (streaks, language, settings), in plain view.

How to trace anything from screen to code

The move: see something on screen → note the exact words it uses → open the file and Ctrl+F for those words → read the few lines around the match. Nearly every "how does that work?" is answered this way in under a minute.
